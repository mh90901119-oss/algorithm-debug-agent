## 三个版本必须分清

1. **公司现状**：根据用户描述，仍是 Skill + 多个 MCP 工具；工具之间主要由模型组织。额外已有 JDWP Plan/断点预检等能力。公司源码、工具实际名称和 Schema 尚未提供。
2. **本地现状**：已经有 Java MCP Server、内部 Coordinator、调查账本、源码查询和结论门禁。不能重复开发这些已有能力；需要修复语义、恢复、资格与交互缺口。
3. **本交付包目标**：保留多工具与模型探索自由；所有工具调用进入同一确定性入口，统一证据身份、执行安全、增量调查与逐条结论资格。不是把全部工具合并成一个工具，也不是新增一个模型。

当前本地 Catalog 有 17 项，这是盘点结果，不是目标数量。公司原有工具必须逐项盘点；合适的工具保留名称和功能，接入共同入口。缺少能力才新增，不能为了与本地数量相同而增删工具。

## 核心承诺与边界

整改能够让同一份证据得到一致的**资格判定**，防止跳过前置条件、引用串案、UNKNOWN 被当支持、丢弃反证、一次不完整采集锁死后续调查。它让模型看到具体缺口和可执行恢复动作。

整改不能仅靠 MCP 或 Coordinator 保证模型发现大型算法的真正根因，也不能证明自由文本因果关系正确。源码理解、竞争解释、核心变量追踪仍需要模型；效果必须由真实复杂 Case 的重复评测验证。不得把“全部工具能调用”作为“推理已收敛”的验收标准。

## 设计与实现的关系

本包修订旧设计中的“一 Gap 一 Plan”“FALSE 必须反驳”“全局假设数量门槛”“状态投影提前决定最终等级”等规则。旧文档中与这些规则相关的完成性描述不作为本包的验证依据。

审批前不修改现行生产契约、旧 Case 或旧设计的 Implemented 状态。批准后按 06 实施，并同步架构索引、ADR-018、当前能力、Schema、Prompt 和验证基线；旧设计对应段落须标明被本设计取代，不能长期保留两套冲突说明。

## 文档验证

从任意工作目录运行本目录的检查器：

```powershell
node <设计包目录>/validate-docs.mjs
```

检查器检查包内链接、JSON 示例、代码映射中已存在的本地文件、设计目标/测试编号闭合和 Markdown 围栏。它不是产品测试、完整 JSON Schema 验证器或 Mermaid 渲染器。执行结果与人工自审记录见 08。

复制到公司后可运行 `node <设计包目录>/validate-docs.mjs --portable`，只检查文档与示例，不要求公司拥有本地文件/工具；公司真实路径/Catalog由P0另外验证。不要以portable通过宣称公司实现兼容。

本包中 `<设计包目录>`、`<公司仓库>` 等为命令占位参数，不是生产硬编码路径；本地模块相对路径只适用于上述 Git 基线。
